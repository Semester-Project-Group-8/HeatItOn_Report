\section{Project Objectives and Requirements}

The main goal of the HeatItOn project is to develop an automated system that can generate cost-efficient heat production schedules for the district heating network in Heatington. The system aims to replace the current manual planning process by providing optimized production strategies that meet heat demand, reduce operational costs, and improve the economic use of electricity. To achieve this, the system must support several key requirements: it must allow users to input relevant source data, manage and select production assets, execute an optimization algorithm that produces feasible and cost-effective schedules, process the resulting output data, and present the results through clear graphical and structured visualizations. The project was developed using a modular software engineering approach, combining a .NET C\# backend, a MySQL database for data storage, and an Avalonia-based frontend. Communication between components was handled through API clients, and the development process included requirement analysis, system design, iterative implementation, integration, and testing to ensure that each module functioned reliably within the overall system.

\section{Problem Statement}

\hspace*{1cm}During this project, the main challenge was to develop an 
automated heat production optimization system for HeatItOn, a district 
heating utility in the city of Heatington responsible for supplying heat 
to approximately 1600 buildings. The desired outcome was a working 
application capable of automatically generating cost-efficient heat 
production schedules, ensuring that the heat demand of the network was 
met at all times while keeping operational costs as low as possible.

The system had to account for different types of production units. Some units simply burn fuel to produce heat, meaning their production costs are fixed and predictable. However, other units are also connected to the electricity grid. A gas motor produces electricity as a byproduct which can be sold back to the grid, while an electric boiler consumes electricity which must be purchased. Since electricity prices change every hour, the effective cost of running these units varies constantly, requiring the optimizer to recalculate and compare the costs of all units on an hourly basis in order to always produce the most economical schedule.  

This required implementing two distinct optimization 
scenarios. The first was a heat-only scenario using three gas boilers 
and one oil boiler. The second was a combined heat and electricity 
scenario using two gas boilers, one gas motor, and one electric boiler. 
Both scenarios also required support for mandatory maintenance periods 
of 30 to 60 hours for designated units, during which the affected unit 
could not participate in the optimization. 

Prior to this project, all heat production planning at HeatItOn was 
carried out manually. Operators had to select which production 
units to run in each hour based on experience and rough cost estimates. 
This made it particularly difficult to react to changing conditions 
such as fluctuating electricity prices or varying heat demand 
throughout the day. As a result, the process was time-consuming and likely to produce 
inefficient decisions.




\subsection*{Problem Analysis}

HeatItOn is a district heating utility in the city of Heatington, responsible for supplying heat to approximately 1,600 buildings via a centralized network. Heat is generated by a combination of traditional heat-only boilers and combined heat and power (CHP) units, which simultaneously produce heat and either generate or consume electricity. 
In a centralized district heating system, hot water is pumped from a central production plant through underground pipes to connected buildings, where it is used for space heating and hot tap water. Once the heat has been extracted, the cooled water flows back to the plant, where it is reheated and recirculated throughout the network.

System will consist of 5 main modules:

\begin{itemize}
    \item Optimizer (OPT)
    \item Data Visualization (DV)
    \item Asset Manager (AM)
    \item Source Data Manager (SDM)
    \item Result Data Manager (RDM)
\end{itemize}

\textbf{Optimizer (OPT):}
Optimizer (OPT): Evaluate all available production units and calculates the most economical heat production schedule, guaranteeing that heat demand across all buildings is met at all times. Each production unit has a fixed cost expressed in DKK per MWh.  The source data for this module is provided in the 2026 Heat Production Optimization – Danfoss Deliveries file.


\textbf{Data Visualization (DV):}
Presents asset, source, and result data in a visual format, enabling users to easily read and analyze the optimization outcomes.

\textbf{Asset Manager (AM):}
Serves as a repository for static system information, providing it available to other system modules. Through the AM, modules can retrieve heating grid information including unit names and graphical representations of the grid.

\textbf{Source Data Manager (SDM):}
Serves as a repository for dynamic system information, storing data in local CSV files. The SDM stores and provides two types of data, the amount of heat demanded by the buildings and the current electricity prices, both of which are updated on an hourly basis.

\textbf{Result Data Manager (RDM):}
Scenario 1 operates on a single district heating network with three gas boilers (GB1, GB2, GB3) and one oil boiler (OB1). The gas boilers have lower production costs, while the oil boiler is more expensive and is therefore reserved for peak demand periods. All boilers maintain constant production costs regardless of the hour of operation.
The optimization strategy prioritizes the cheapest gas boiler first, adding output from more expensive units only when needed to meet the total heat demand. One of the gas boilers must also undergo a scheduled maintenance period of between 30 and 60 hours, during which it is taken offline and produces 0 MW.



\subsection*{Scenarios}

\subsubsection*{Scenario 1 (Heat only)}

Scenario 1 uses a single district heating network with three gas boilers (GB1, GB2, GB3) and one oil boiler (OB1). The gas boilers are cheaper, while the oil boiler has higher production costs and is mainly used in peak demand periods. All boilers have constant production costs that do not depend on the hour of operation. Strategy for scenario one is to run the cheapest gas boiler first and then add production from the more expensive boilers if needed to meet the heat demand. There should also be chosen a period of 30 to 60 hours when one of the gas boilers will be down due to maintenance.

\subsubsection*{Scenario 2 (Heat and electricity)}

Scenario 2 operates on a network with two gas boilers (GB1, GB3), one gas motor (GM1), and one electric boiler (EB1). The gas motor produces electricity that can be sold on the market, while the electric boiler consumes electricity that must be purchased.
When electricity prices are high, the gas motor is prioritized, as selling electricity generates additional income. When prices are low, the electric boiler becomes the preferred unit, as buying electricity is cheaper. Unit selection is determined each hour by calculating and comparing the net production cost for each unit.


The project is based on data delivered by Danfoss, including:

\begin{itemize}
    \item Graphical representation of the district heating network
    \item Configuration parameters for each production unit (image, produced heat, produced/consumed electricity, primary energy consumption, production costs, CO2 emissions)
    \item Heat demand and electricity prices for a 14-day winter period with 1-hour resolution
    \item Heat demand and electricity prices for a 14-day summer period with 1-hour resolution
\end{itemize}

If time allows, the project could be extended with additional visualization libraries, database storage, the ability to enable or disable individual units directly from the user interface, alternative configurations for Scenario 2, and implementing APIs and an API client for reading electricity prices from Energinet.dk. 


\section{Functional Requirements}

\subsection*{Scenario 1}

\subsubsection*{1. Source Data Manager (SDM) \& Result Data Manager (RDM)}
\textit{Components that handle where the data comes from and where it goes.}

\begin{itemize}
    \item The user should be able to receive input data.
    \item The user should be able to retrieve input data.
    \item The user should be able to output data. \textbf{[Database integration]}
\end{itemize}

\subsubsection*{2. Asset Manager (AM)}
\textit{Component that keeps track of the physical boilers and their constraints.}

\begin{itemize}
    \item The user should be able to upload assets from csv file.
    \item The user should be able to add asset.
    \item The user should be able to edit assets. \textbf{[Boiler definitions]}
    \item The user should restrict the maximum heat output of each unit as follows: GB1 to 3.0 MW, GB2 to 2.0 MW, GB3 to 4.0 MW, and OB1 to 6.0 MW. \textbf{[Capacity constraints]}
\end{itemize}

\subsubsection*{3. Optimizer (OPT)}
\begin{itemize}
    \item The user should be able to schedule the cheapest boilers first to fulfill the district's heat demand. \textbf{[Cost-based dispatch]}
    \item Based on production costs, the optimizer should prioritize boilers in the following strict order: GB1 (510 DKK), GB2 (540 DKK), GB3 (580 DKK), OB1 (690 DKK). \textbf{[Dispatch order]}
    \item The user should only use the more expensive oil boiler (OB1) to supplement heat during peak demand periods when the gas boilers cannot fulfil the total demand. \textbf{[Peak demand handling]}
    \item The user should be capable of optimizing units separately for both a winter period and a summer period. \textbf{[Seasonal optimization]}
    \item The optimizer should remove a designated gas boiler from the available pool of units during its scheduled maintenance period, ensuring it produces 0 MW. \textbf{[Maintenance logic]}
\end{itemize}

\subsubsection*{4. Data Visualization (DV) / User Interface}
\begin{itemize}
    \item The UI should validate that the user's selected maintenance duration is a minimum of 30 hours and a maximum of 60 hours. \textbf{[Maintenance constraints validation]}
    \item The UI should display a chart or graph that visually compares the total heat demand against the individual heat output contributions of GB1, GB2, GB3, and OB1 over time. \textbf{[Result graphing]}
    \item The UI should provide a way for the user to choose an obligatory maintenance period for one unit in both the summer and winter periods. \textbf{[Maintenance scheduling]}
\end{itemize}

\subsection*{Scenario 2}

\subsubsection*{1. Source Data Manager (SDM) \& Result Data Manager (RDM)}
\textit{Component that handle a crucial data stream: electricity prices.}

\begin{itemize}
    \item The user should be able to retrieve hourly electricity prices data from data base.
    \item The user should be able to retrieve hourly heat demand data from the database. \textbf{[Market data retrieval]}
\end{itemize}

\subsubsection*{2. Asset Manager (AM)}
\textit{The physical assets include units that interact with the power grid.}

\begin{itemize}
    \item The user should be able to upload assets from csv file. \textbf{[Unit registration]}
    \item The user should be able to limit the maximum heat output of each unit: GB1 to 3.0 MW, GB3 to 4.0 MW, GM1 to 5.3 MW, and EB1 to 6.0 MW. \textbf{[Heat capacity constraints]}
    \item The user should account for electricity production and consumption capacities, specifically noting that GM1 produces up to 3.9 MW of electricity, while EB1 consumes up to 6.0 MW (-6.0 MW). \textbf{[Electricity constraints]}
\end{itemize}

\subsubsection*{3. Optimizer (OPT)}
\begin{itemize}
    \item The user should be able to calculate the net production costs for the electricity-producing/consuming units based on the fluctuating electricity prices. \textbf{[Dynamic net cost calculation]}
    \item The optimizer should prioritize running the gas motor (GM1) during periods of high electricity prices. \textbf{[High-price optimization logic]}
    \item The optimizer should prioritize running the electric boiler (EB1) during periods of low electricity prices. \textbf{[Low-price optimization logic]}
    \item The optimizer should actively prevent the gas motor (GM1) from running during summer periods with negative electricity prices (to avoid paying for produced electricity).
    \item The optimizer should recognize the electric boiler as an extra income source during negative price hours. \textbf{[Negative price handling]}
    \item The optimizer should completely remove either GB1 or GM1 from the optimization calculations during its scheduled maintenance period. \textbf{[Maintenance logic]}
\end{itemize}

\subsubsection*{4. Data Visualization (DV) / User Interface}
\begin{itemize}
    \item The UI should allow the user to select an obligatory maintenance period for either GB1 or GM1, enforcing a duration between 30 and 60 hours. \textbf{[Maintenance scheduling]}
    \item The UI should display a graph comparing the total heat demand against the individual heat output contributions of GB1, GB3, GM1, and EB1 over time. \textbf{[Result graphing]}
\end{itemize}

\subsection*{General App Navigation \& UI}
\textit{Requirements that cover the flow of the application from the user's perspective.}

\begin{itemize}
    \item Upon launch, the application should display a home screen allowing the user to explicitly select between Scenario 1 and Scenario 2. \textbf{[Startup Page]}
    \item The user interface should allow user to navigate  between scenarios easily. \textbf{[Scenario navigation]}
\end{itemize}

\subsection*{System Architecture \& Data Handling}
\textit{Requirements that cover how the app manages data and how the 5 components talk to each other.}

\begin{itemize}
    \item The user should be able to use a database system to save and retrieve data. \textbf{[Database storage]}
\end{itemize}

\subsection*{Advanced Configuration \& Comparison}
\textit{Requirements that give the user more control over the optimization process.}

\begin{itemize}
    \item The UI should provide a mechanism for the user to dynamically activate or deactivate individual heating units from being considered in the optimizer's calculations. \textbf{[Dynamic unit toggling]}
    \item The system should allow the user to run custom scenario with configurations setted by user. \textbf{[Custom scenario configuration]}
    \item The Data Visualization module should provide results of different configured scenarios for result comparison. \textbf{[Comparison metrics]}
\end{itemize}

\section{Non-Functional Requirements}

\subsection*{1. Performance \& Efficiency}
\begin{itemize}
    \item The system should complete all optimization calculations within 3 seconds of the user clicking or "Optimize." \textbf{[ Optimization speed ]}
    \item The system should completely render the resulting graphs within 3 seconds of the user clicking "Run". \textbf{[ Processing speed ]}
    \item The system and database should be capable of efficiently loading, processing, and aggregating a full month of hourly data ( approx. 720-744 data points ) without UI freezing or lag. \textbf{[ Data volume handling ]}
\end{itemize}

\subsection*{2. Environment \& Portability}
\begin{itemize}
    \item The application should be fully cross-platform compatible, executing reliably on Windows, macOS, and Linux operating systems. \textbf{[ Cross-platform compatibility ]}
\end{itemize}

\subsection*{3. Usability \& Localization}
\begin{itemize}
    \item The entire user interface, including all menus, labels, and error messages, should be written in English. \textbf{[ UI Language ]}
    \item All financial values, production costs, and revenues should be calculated and displayed strictly using Danish Kroner (DKK). \textbf{[ Currency localization ]}
    \item The resulting visualization for a month of data should be highly readable, formatting the daily boiler usage as a stacked chart (matching the total heat demand on the Y-axis, and days of the month on the X-axis) alongside a daily cost graph. \textbf{[ Visualization clarity ]}
\end{itemize}

\subsection*{4. Reliability \& Robustness}
\begin{itemize}
    \item The system should not crash if the Energinet.dk API is unresponsive or if the user loses internet connection. \textbf{[ System stability ]}
    \item In the case of an API failure, the system should handle the error by displaying a clear, understandable error feedback message or popup to the user. \textbf{[ Exception handling ]}
\end{itemize}


\section{Target User Persona}
The system is designed with a specific target audience in mind. To ensure an optimal user experience, the ideal user (persona) interacting with this system is assumed to have the following profile:
\begin{itemize}
    \item Be able to read in English
    \item Be able to navigate a simple UI
    \item Have a basic understanding of the district heating problem being solved by the system
    \item Be able to read and understand basic input/output data
\end{itemize}
